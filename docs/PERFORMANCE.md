# WorkMesh 性能与扩展设计

版本：1.0
状态：性能设计阶段

## 1. 设计目标

WorkMesh 不仅需要支持小规模 CSV 文件导入，还应为未来大量企业业务数据接入做好准备。

性能设计重点：

- 文件上传和解析
- 数据标准化
- 批量数据库写入
- 大数据量查询
- 多任务执行
- AI 分析成本和响应时间
- 内存及 CPU 资源控制

本文中的数据规模是架构规划目标，不代表当前版本已经达到相应性能。

## 2. 数据规模规划

### 阶段一：个人和小团队

规划规模：
- 累计记录：1万至10万条
- 数据库：SQLite
- 部署：本地 Mac
- 导入：CSV / Excel
- 分析：本地统计和基础 AI 分析

### 阶段二：中型企业

规划规模：
- 累计记录：10万至100万条
- 数据库：PostgreSQL
- 支持后台任务
- 支持分块解析
- 支持批量写入
- 支持分页查询
- 支持多数据源接入

### 阶段三：大型企业

规划规模：
- 百万至千万级记录
- 独立任务队列
- 多工作进程
- 对象存储
- 专用搜索和分析引擎
- 增量同步
- 完整性能监控

实际承载能力需要通过目标硬件和并发测试确认。

## 3. 文件导入性能

### 3.1 避免一次性加载大文件

不应对所有大文件直接执行全量读取并保留多个完整 DataFrame 副本。

CSV：
- 支持分块读取。
- 使用 Pandas chunksize。
- 按批次处理和写入。

Excel：
- 优先支持 XLSX。
- 大文件采用只读模式或流式解析方案。
- 限制最大行数、列数和文件大小。
- 对超出资源限制的文件给出明确提示。

### 3.2 暂存机制

导入文件应先进入受控临时目录。

要求：
- 文件名安全处理。
- 文件格式校验。
- 文件大小限制。
- 解析失败后清理临时文件。
- 成功或失败后按保留策略清理。

### 3.3 分块处理

初始建议每批处理5000条记录。

该值属于可配置的初始参数，需要通过实际测试调整。

处理过程：
1. 读取一批数据。
2. 执行字段映射。
3. 执行数据标准化。
4. 执行数据质量检查。
5. 批量写入数据库。
6. 更新任务进度。
7. 继续处理下一批。

## 4. 后台任务

大文件导入不应长期占用页面请求。

任务应记录：
- task_id
- workspace_id
- batch_id
- task_type
- status
- total_records
- processed_records
- success_records
- failed_records
- started_at
- completed_at
- error_message

任务状态：
- pending
- running
- completed
- failed
- cancelled

后续支持：
- 进度查询
- 任务取消
- 失败重试
- 幂等处理
- 任务超时

当前本地 MVP 可以先实现轻量任务管理，不提前引入 Redis 和 Celery。

## 5. 数据库性能

### 5.1 写入优化

- 使用批量 INSERT。
- 使用事务控制。
- 避免逐条提交事务。
- 控制单次事务大小。
- 处理重复数据时使用明确的去重规则。

### 5.2 查询优化

- 使用分页查询。
- 避免一次性加载全部记录。
- 对常用过滤字段建立索引。
- 避免无必要的 SELECT *。
- 定期检查慢查询。

建议重点关注：
- workspace_id
- batch_id
- feedback_time
- version
- error_code
- source_type

索引应根据实际查询模式调整。

### 5.3 SQLite 约束

当前使用 SQLite。

可以考虑：
- WAL 模式。
- 外键约束。
- 合理事务。
- 限制并发写入。
- 定期备份。

SQLite 适合当前本地单机 MVP，不作为未来高并发企业部署的最终数据库方案。

## 6. 查询和页面性能

- 默认分页展示。
- 大表不直接全部渲染到 Streamlit。
- 对统计结果进行缓存。
- 避免每次页面刷新都重复执行完整分析。
- 根据筛选条件执行数据库查询。
- 长时间任务通过状态轮询展示结果。

## 7. AI 分析性能和成本

不将所有原始反馈直接发送给大模型。

建议流程：
1. SQL/Python 完成基础统计。
2. 按问题类型归并。
3. 提取代表性样本。
4. 控制输入 Token 数量。
5. 分批分析复杂任务。
6. 汇总分析结果。
7. 保存证据和模型调用记录。

记录：
- 模型名称
- 请求时间
- 响应时间
- 输入 Token
- 输出 Token
- 请求状态
- 错误信息
- 成本估算

## 8. 资源限制

以下参数应支持配置：
- 最大上传文件大小
- 最大记录数
- 最大列数
- 单批处理记录数
- 最大任务运行时间
- 最大并发任务数
- AI 输入 Token 限制

初期默认值需要通过本地测试确定。

## 9. 性能监控

建议记录：

| 指标 | 说明 |
|---|---|
| file_size | 上传文件大小 |
| parse_duration | 文件解析耗时 |
| normalize_duration | 数据标准化耗时 |
| write_duration | 数据库写入耗时 |
| total_duration | 导入总耗时 |
| records_per_second | 每秒处理记录数 |
| peak_memory | 峰值内存 |
| query_duration | 查询耗时 |
| task_failure_rate | 任务失败率 |
| llm_latency | 模型响应耗时 |
| llm_token_usage | Token 消耗 |

## 10. 性能测试计划

使用不同规模的测试数据：

- 1000 条
- 10000 条
- 50000 条
- 100000 条

测试项目：
- 文件解析耗时
- 标准化耗时
- 数据库写入耗时
- 数据库查询耗时
- 峰值内存
- 页面响应情况

测试环境：
- 当前 Intel Mac
- 当前 Python 环境
- SQLite
- 实际项目依赖版本

记录真实测试数据，不使用未经验证的性能数字作为产品宣传。

## 11. 性能演进原则

1. 先测量，再优化。
2. 先优化数据处理和 SQL，再增加基础设施。
3. 避免过早引入复杂分布式组件。
4. 性能优化不能牺牲数据准确性。
5. 大规模任务必须支持失败恢复和数据追溯。
